# 本地阅卷耗时记录说明（2026-10-21）

本文说明新版的计时口径、日志位置和排查方法。功能不增加截图、不主动调用模型、不重试提交，也不减少原有的防串分、输入权限或提交确认校验。


## 保存位置

默认数据目录为 `%USERPROFILE%\.deskgrade\data`，性能记录位于其 `performance` 子目录，例如：

```text
%USERPROFILE%\.deskgrade\data\performance\performance-2026-10-21-000001.jsonl
```

每个结束的计时周期追加一行 JSON，事件名为 `ATTEMPT_TIMING_SUMMARY`。不是每份答卷生成一个独立文件。文件按本地日期分组，达到 16 MiB 后新建序号文件，不按运行日志的 7 天规则删除历史。自定义数据目录时，使用该目录下的 `performance`。

性能日志只包含任务、答卷、调用的标识，阶段名称、耗时、计数和有限诊断码；不写入 Key、服务端地址、学生原文、图片、截图哈希或框选坐标。原有完整阅卷账本和 `records` 日志继续独立保存，性能文件不能代替提交账本。

### 中文汇总查看

仓库提供 `scripts/summarize-performance.ps1`，便携发行目录的 `docs` 和 EXE 安装目录的 `app/docs` 也包含该脚本。默认读取本机最新批次的最近 20 条摘要，输出逐题总耗时、模型等待、截图次数与时长、互斥主阶段的平均占比及重叠细项。已观察提交进度和异常/未确认样本分组计算，不混成一个平均值。

在仓库根目录的 PowerShell 中执行：

```powershell
.\scripts\summarize-performance.ps1
.\scripts\summarize-performance.ps1 -Last 100
```

可用 `-Directory` 指定某个 `performance` 文件夹，或 `-RunId` 指定批次。脚本只读，不清理、不修复、不上传历史。读取范围有界（最多最新 10 段、每段 16 MiB、单行 16 KiB、共 10000 行）；超限、损坏或未来不兼容格式会提示忽略数量，不应把有限窗口结果误认为全部历史。

## 一份答卷的总耗时

`totalMs` 从本份答卷周期开始计时：首次启动或重新采集未提交答卷时包含 `PRECHECK`，后续连续答卷从 `WAIT_READY` 起。它包含前置就绪等待、截图及证据保存、模型请求、分数校验、填分、读回、提交、确认，以及确认后等待下一份答卷准备好的时间；提前暂停、停止、失败或完成任务时，在该终点结束。

正常连续阅卷时，本份周期结束于下一份答卷通过新鲜性检查，随后下一份另起计时周期。达到用户设置的题数、网站已完成、发生安全停止等情况，不要求继续进入下一题才生成本份摘要。最后一份的耗时因此不必包含与中间题相同的下一页等待。

每个新答卷周期只输出一次已结束摘要。已经确认的答卷若因等待下一页而暂停，其摘要在暂停时结束；后续恢复只观察旧答卷到下一页的过程，不为该旧答卷重复创建摘要。这段恢复等待也不并入下一份的新周期。因此，不能将全部 `totalMs` 相加，直接当成“第一次开始到最后结束”的完整墙钟时长。

若在创建答卷记录前就停止，仍可能输出诊断摘要，此时 `attemptId` 为 `null`。应同时使用 `runId`、`traceId`、`ordinal` 关联记录，不要把 `ordinal` 当成网站学生编号。

计时使用单调时钟，输出单位为毫秒，保留三位小数；`startedAt`、`completedAt` 是供人工关联的时间戳。不要用两个时间戳相减替代 `totalMs`，系统校时可能影响时间戳，但不改变单调计时。

## 已观察到提交进度的耗时

`untilAcknowledgedMs` 表示从本份周期开始，到程序观察到符合当前平台协议的确认/页面进度，并完成对应本地账本记录的耗时。没有观察并记录该证据时为 `null`，不是 `0`。

这个字段不证明阅卷平台服务端已保存分数，也不证明平台后台事务已最终完成。自动跳下一题、局部成功提示等只是不同平台下的可观察证据，具体强度仍应结合原记录的确认类型判断。提交结果未知的安全停止不会因为存在性能日志而变成“提交成功”。

## 主阶段与嵌套操作不要混加

摘要提供两套不同口径：

| 字段 | 用途 | 能否求和 |
| --- | --- | --- |
| `phases` | 按状态划分整份周期，如 `WAIT_READY`、`CAPTURING`、`GRADING`、`WAIT_ACK`、`WAIT_NEXT` | 主阶段互斥，原始纳秒总和对应总耗时；毫秒四舍五入后可有微小误差 |
| `metrics` | 具体操作的累计耗时和次数，可嵌套 | 不能直接相加作为总耗时 |
| `modelCalls` | 每次主/备用模型请求的等待和回调排队 | 已包含在相关主阶段内，不能再叠加 |

例如，“提交操作”可能包含“最后读回分数”，最后读回又包含“剪贴板读分”和多次保护性截图。因此 `SUBMIT_ACTION`、`FINAL_SCORE_READBACK`、`CLIPBOARD_READ`、`VERIFY_TARGET`、`CAPTURE_TOTAL` 之间会重叠。相加可能远大于实际墙钟时间，这是嵌套计量，不是重复执行的证据。

`count` 是该指标实际被计量的调用次数；`elapsedMs` 是这些调用的累计耗时，不是平均值。可用 `elapsedMs / count` 估算该层操作的平均耗时，但要先确认该指标包含哪些保护操作。

## 操作指标的实际范围

| 指标 | 包含内容 |
| --- | --- |
| `OBSERVE` | 平台观察及其内部必要截图、画面一致性检查 |
| `CAPTURE_EVIDENCE` | 获取本题答题证据和用于防串分的对应证据 |
| `EVIDENCE_SAVE` | 本地证据元数据处理；当前不保存答卷图片 |
| `JOURNAL_WRITE` | 已有持久账本检查或写入，不包括性能摘要自身的写入 |
| `MODEL_DISPATCH` | 建立并派发异步请求的同步部分，不代表整个模型等待 |
| `VALIDATE_GRADE` | 返回评分的本地合法性校验 |
| `FILL_SCORE` / `READ_SCORE` | 填分或读分及相应保护检查 |
| `VERIFY_TARGET` | 当前答卷/目标的校验，可能包含保护性截图 |
| `SUBMIT_ACTION` / `NEXT_ACTION` | 已授权的提交或下一题操作及其原有检查 |
| `FINAL_SCORE_READBACK` | 点击提交前再次读回实际输入分数，包括原有目标校验 |
| `CLIPBOARD_READ` | 实际控件点击、复制、剪贴板读取/等待/恢复，以及期间的权限和目标校验；不是纯剪贴板等待 |
| `NATIVE_SUBMIT_CLICK` | 原有底层提交调用，包含权限、目标窗口等保护；不是单独一次系统鼠标调用的纯耗时 |

底层截图还拆分为：

| 指标 | 包含内容 |
| --- | --- |
| `CAPTURE_TOTAL` | 一次实际截图调用的完整耗时及整体成功/失败 |
| `CAPTURE_BOUNDARY_PREPARE` | 截图前清除扫描覆盖层和等待原有渲染边界 |
| `CAPTURE_SAFETY_BEFORE` / `CAPTURE_SAFETY_AFTER` | 截图前后的窗口及目标安全检查 |
| `CAPTURE_RAW` | 原始屏幕采集与匹配分辨率图像的选取 |
| `CAPTURE_PIXEL_COMPARE` | 0.2.4 新增：新鲜截图与上一成功帧的完整原始像素精确比较及缓存适用性检查 |
| `CAPTURE_PNG_ENCODE` | 实际 PNG 编码；0.2.4 逐像素复用命中不进入此阶段 |
| `CAPTURE_PNG_REUSE` | 0.2.4 新增：仅对同一绑定、尺寸、受支持图像布局且原始像素全部相同的新截图复用 PNG 字节；不是复用旧截图或旧时间戳 |
| `CAPTURE_DIGEST_AND_RESULT` | 摘要计算和截图结果对象构造 |
| `CAPTURE_BOUNDARY_CLOSE` | 截图边界退出与资源清理 |

底层截图次数可能高于模型调用次数：稳定性验证、防串分、填分前后、提交前读回及页面进度观察均可能需要截图。这些只是为已有动作计时，没有为了日志额外截图或等待。

启动批次前的存储探测、`beginRun`，以及人工核对未知提交，不在本份计时范围内。性能摘要自身的一次同步写盘发生在计时结束后，不计入 `totalMs`。上述边界意味着它是逐份阅卷流程诊断，不是程序进程全部 CPU/磁盘开销统计。

截图明细的 `failures` 不应单独用来判断每个叶子阶段成功与否：当前叶子记录只提供已进入阶段的耗时；截图整体失败通过 `CAPTURE_TOTAL` 的失败计数体现。未出现的叶子指标也可能是流程提前终止，不能当成耗时为零且执行成功。

## 模型耗时的解释

`modelCalls` 分别记录 `PRIMARY` 和实际使用的 `FALLBACK`。`elapsedMs` 是请求开始到供应商适配器完成的整体等待，包括本地请求准备、网络传输、远端排队/处理、响应读取解析，以及原本策略允许的安全重试等待。它不是供应商给出的“纯模型推理耗时”，也不能据此推算 Token 数或计费金额。

`callbackQueueMs` 单独表示请求完成后，回调等待阅卷串行执行器处理的时间。若请求已完成但停止时回调尚未执行，摘要只计到停止时刻。

`outcome` 的含义如下：

- `SUCCEEDED`：供应商调用正常完成并返回结果。结果仍可能是 `UNABLE`，也可能随后未通过评分校验；不代表已经得到可用分数或提交成功。
- `FAILED`：供应商调用以异常结束。不代表程序点击过提交。
- `IN_FLIGHT`：生成摘要时该调用仍未完成。不虚构为成功或失败；之后迟到的调用/回调不会修改已经结束的性能快照，也不会计入下一份答卷。

是否评分有效、有没有实际填分或提交、平台提交证据是否成立，应以原有阅卷记录和状态为准。性能结果不授予任何输入权限，不补交未知结果。

## 中断、历史与写入失败

只在周期结束时追加摘要，没有每次页面观察都写一条性能文件。程序仍在执行、进程崩溃、强制结束进程或直接断电时，可能没有本份摘要；不能把“没有摘要”等同于“没有调用模型”或“没有提交”。未结束模型请求的实际账本记录仍按原有策略处理。

性能文件是辅助诊断：写入失败会发出安全警告，例如 `PERFORMANCE_LOG_WRITE_FAILED` / `LOCAL_PERFORMANCE_LOG_UNAVAILABLE`，但不会因此修改评分、补发请求、重放点击或放宽安全校验。完整本地账本/提交意图的存储失败，仍按原有必须停止的策略执行，不能与辅助计时失败混淆。

新版只能从实际运行时采集这些时间。旧记录若没有各阶段开始/结束信息，不能可靠重建截图、读分、提交或模型推理耗时；日志里不补造历史数据。

## 排查顺序

1. 先按 `runId`、`attemptId` 关联原有阅卷记录，确认停止阶段、诊断码和实际提交状态。
2. 查看 `totalMs` 与互斥 `phases`，判断等待主要出现在模型、页面就绪、提交确认还是下一页。
3. 若为模型等待，查看 `modelCalls.elapsedMs` 和 `callbackQueueMs`，不要仅看同步 `MODEL_DISPATCH`。
4. 若为本地操作，沿父指标查看读分、保护校验和截图叶子指标，注意重叠，结合 `count` 判断是单次较慢还是已有保护被多次执行。
5. 只有在明确耗时来源后再决定优化；性能日志本身不改变防串分、错误停止和禁止重复提交的边界。

## 实现边界核对

当前源码中，Controller 的已计时平台调用为同步链路；手动适配器内部的自身校验、驱动读分和原生输入权限回调，继承并恢复同一线程的计时上下文，因此其中实际发生的截图可以归属本份答卷。后台窗口监视器使用独立线程且只检查窗口，不进入截图链路；独立 UI 截图没有本份上下文，不会误计入正在阅卷的答卷。

这属于本版代码链路与合成测试的结论，不代表真实网站耗时已经完成采集。若未来把截图或平台操作改为跨线程异步执行，需要明确传递原计时上下文；不能依赖线程池自动继承，更不能把迟到结果归到新的答卷。
